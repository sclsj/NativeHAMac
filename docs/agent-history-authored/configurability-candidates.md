This is a selection report, not an implementation plan or an assertion that every candidate should ship. It audits NativeHA at `b5b5c2dde234e208201a3b32a4b6b852bb22a069` against hass-frontend at `dbc68cc5c59ce720a47e5f4aa3d9d7a68d84fdbd`. The ranking favors settings that represent a real product, performance, or resource tradeoff. It deliberately excludes secrets, entity-specific profile data, and reference semantics that are matters of correctness rather than preference.

## 1. Graph time-range policy and selector

- **Current NativeHA behavior:** `Sources/NativeHAMac/AppConfig.swift` defines `defaultGraphHours = 1` and `graphHourOptions = [1, 3, 6, 12]`. `DashboardView.topBar`, `DashboardViewModel.setGraphHours(_:)`, `historyRequests()`, and `cleanCards(_:)` make that one selection overwrite all displayed history cards. `CardViews.swift` also hardcodes `hours: 24` in the fan, switch, and sensor detail histories. The user has now clarified that the separate Home/3h/12h hass views are a workaround and their real intent is a knob/selection that changes graph time range; superficial differences between those hass views are not intended product differences.
- **Relevant hass behavior/default:** `src/panels/lovelace/cards/hui-history-graph-card.ts` defines `DEFAULT_HOURS_TO_SHOW = 24` and otherwise honors each card's `hours_to_show`. The current live Lovelace dashboard encodes 1h/3h/12h through cards/views, but that representation is not the user's intended NativeHA UX.
- **Proposed `AppConfig` surface:** `static let graphTimeRangePolicy: GraphTimeRangePolicy`, where the type contains `mode: GraphTimeRangeMode`, `options: [GraphTimeRange]`, `defaultSelection: GraphTimeRange`, and `detailDefault: GraphTimeRange`. `GraphTimeRange` should be a validated hours/minutes value rather than a bare `Int`. Default: `.globalSelection`, options equivalent to `[1h, 3h, 6h, 12h]`, default `1h`, detail default `24h`, preserving current NativeHA behavior and the user's stated deviation. A mode such as `.lovelacePerCard` can preserve hass behavior when desired.
- **Alternatives and purpose:** `.globalSelection` changes all dashboard graphs together; `.perCardSelection` allows independent graph controls; `.lovelacePerCard` follows server configuration exactly. Additional useful options such as 30m or 24h can be added without changing view code. The explicit scope avoids an implementation silently choosing whether a control affects one card, the current view, or every graph.
- **Implementation touch points:** replace the two bare graph constants; update `DashboardView.topBar`, `DashboardViewModel` history keys/requests/card cleaning, `UnitGraph` window bounds, all `DetailHistoryGraph(... hours: 24)` call sites, and later `history/stream` subscription keys. Store runtime selection state separately from immutable configuration.
- **Test/validation impact:** convert `CardReferenceContractTests.testHistoryCardUsesItsOwnHoursToShow` into policy-mode tests; verify each selection changes request/subscription windows and labels, switching back is cache-safe, independent-card mode does not leak between cards, and the current global default remains 1h. Live-smoke the selector against data covering every option.
- **Risk:** changing range must cancel/replace the correct stream and must not mix cached histories under an old key. Large ranges increase payload and memory. A global override can conceal deliberate per-card ranges unless its active state is visible.
- **Provenance:** `USER_EXPLICIT` — the range selector and the meaning of the hass 3h/12h views are direct instructions in the current request.

## 2. Graph downsampling strategy and detail budget

- **Current NativeHA behavior:** `GraphBitmapRenderer.targetPointCount(plotWidth:seriesCount:)` returns `max(Int(plotWidth * 2) / seriesCount, 80)`. `GraphMinMaxCache.downsample(in:target:)` then emits time-ordered min/max points per equal-count bucket with first/last endpoints. The benchmark target already implements `.none`, `.stride`, `.minMax`, `.firstLastMinMax`, and `.lttb` in `Sources/GraphBench/GraphBench.swift`, but production is fixed to min/max.
- **Relevant hass behavior/default:** `src/components/chart/state-history-chart-line-data.ts` sets `sampling: "minmax"`. `ha-chart-base.ts` replaces that with `downSampleLineData(data, clientWidth * devicePixelRatio, minX, maxX)`. `src/components/chart/down-sample.ts` uses time frames and retains min/max in source order; its optional mean mode is used by other callers, and `statistics-chart-data.ts` uses LTTB for one band-rendering case. Thus min/max is the reference default, while alternative algorithms are already credible rather than hypothetical.
- **Proposed `AppConfig` surface:** `static let graphSamplingPolicy: GraphSamplingPolicy`, containing `strategy: GraphSamplingStrategy`, `detailsPerPixel: CGFloat`, `minimumDetailsPerSeries: Int`, and `divideBudgetAcrossSeries: Bool`. Default: `.nativeMinMax`, `2`, `80`, `true`, exactly preserving production NativeHA. Provide `.referenceTimeFrameMinMax` as the closest hass mode.
- **Alternatives and purpose:** `.referenceTimeFrameMinMax` prioritizes parity across irregular time spacing; `.nativeMinMax` keeps current performance; `.lttb` favors overall visual shape; `.none` provides a diagnostic/fidelity oracle for bounded data; `.mean` is useful for trend views where spikes are intentionally not the product. `.stride` should remain benchmark/debug-only unless explicitly selected because it can miss extrema. The detail budget can scale with backing pixels or logical pixels.
- **Implementation touch points:** make `GraphBitmapRenderer` accept the policy, generalize `GraphMinMaxCache` or add strategy-specific samplers, promote proven algorithms from `GraphBench` rather than duplicating them, include the policy in render/cache tokens, and pass it through dashboard and detail graphs.
- **Test/validation impact:** add adversarial fixtures for isolated spikes, irregular timestamps, duplicate times, monotonic data, empty/small ranges, and multiple series. Compare every lossy mode with `.none` for documented invariants; benchmark actual and stress histories; verify the default produces byte/geometry-equivalent output where feasible.
- **Risk:** exposing a mode does not make lost extrema acceptable. Some strategies have different computational complexity and cache needs, and changing a policy without invalidating prepared/render caches can show stale output. Invalid budgets must be clamped.
- **Provenance:** `USER_EXPLICIT` — the current request specifically names ambiguous downsampling choices as behavior that should be configurable.

## 3. Graph render-resolution policy

- **Current NativeHA behavior:** `BitmapLineChart.scheduleViewportRender` and `scheduleLiveDataRender` both use `NSScreen.main?.backingScaleFactor ?? 2`; `GraphBitmapRenderer` allocates `width * scale * height * scale * 4` bytes. Rendering is therefore always at the main screen's full backing scale, even when a window is on another screen. `README.md` says this should be controlled by `renderInteractiveGraphsAtFullResolution`, but no such current `AppConfig` key exists.
- **Relevant hass behavior/default:** `ha-chart-base.ts` gives the downsampler a detail budget based on `clientWidth * window.devicePixelRatio`; browser canvas/ECharts therefore also treats device pixels as the fidelity baseline.
- **Proposed `AppConfig` surface:** `static let graphRenderResolution: GraphRenderResolutionPolicy = .displayBackingScale(fallback: 2)`. Suggested enum cases: `.displayBackingScale(fallback:)`, `.fixed(CGFloat)`, and `.cappedBackingScale(max:fallback:)`. The view should use the hosting window/screen's scale instead of always `NSScreen.main`.
- **Alternatives and purpose:** full backing scale preserves the user's stated accuracy priority; fixed 1x reduces bitmap memory and render cost for remote sessions or debugging; a cap bounds pathological large-window/multi-display cost; fixed 2x makes screenshots deterministic. This is a measurable quality/resource control, not an invitation to silently lower quality.
- **Implementation touch points:** `BitmapLineChart` scale selection, display-change invalidation, render tokens, `GraphBitmapRenderer` input validation, GUI test injection, and the stale README reference. Consider a maximum pixel-count guard in the same typed policy.
- **Test/validation impact:** assert image dimensions and plot geometry at 1x/2x and after simulated display changes; compare line visibility and labels; benchmark CPU and peak allocation at large graph sizes. The default must keep the existing 2x results on this machine.
- **Risk:** lower scales blur thin lines/text overlays and can violate reference fidelity. Very high or unbounded scales can allocate large buffers. Failing to rerender when a window moves screens leaves a mismatched bitmap.
- **Provenance:** `AGENT_SUGGESTED_FOR_SELECTION` — the tradeoff is code-grounded and the README hints at it, but no provenance-corrected user instruction selects a resolution knob.

## 4. Typed live-update and render scheduling policy

- **Current NativeHA behavior:** `AppConfig.swift` exposes three raw nanosecond integers: `realtimeUpdateCoalesceNanoseconds = 50_000_000`, `liveGraphDataRenderDelayNanoseconds = 120_000_000`, and `liveGraphInteractionDeferNanoseconds = 500_000_000`. `DashboardViewModel.queueStateUpdate` and `BitmapLineChart.scheduleLiveDataRender` consume them directly.
- **Relevant hass behavior/default:** `src/components/chart/state-history-chart-line-data.ts` disables animation for data updates, while `ha-chart-base.ts` contains its own update gating and a five-millisecond deferred ZRender flush only for datasets above 10,000 points. These are implementation-specific reference choices, not equivalent universal delays.
- **Proposed `AppConfig` surface:** replace the three unrelated integers with `static let liveUpdateScheduling = LiveUpdateSchedulingPolicy(stateCoalescing: 0.05, idleGraphRenderDelay: 0.12, postInteractionQuietPeriod: 0.5)`, using `TimeInterval` fields for Swift 5.6 compatibility and one validated conversion to nanoseconds. Defaults preserve current behavior exactly.
- **Alternatives and purpose:** a low-latency profile can use zeros or shorter delays; a low-power/large-dashboard profile can batch longer; tests can use an immediate policy. Grouping the settings makes their ordering constraints and purpose visible and avoids unit mistakes.
- **Implementation touch points:** `AppConfig`, `DashboardViewModel.queueStateUpdate`, `BitmapLineChart.scheduleLiveDataRender`, task cancellation, and test-only dependency injection of the scheduling policy/clock.
- **Test/validation impact:** use a controllable clock/scheduler to prove burst coalescing, trailing update delivery, cancellation, no starvation during continuous events, and priority of viewport interaction. Benchmark update bursts at representative entity counts.
- **Risk:** long values create stale UI; zero values can cause render storms; a quiet period that is continually reset can starve graphs. Invalid/overflowing intervals require validation.
- **Provenance:** `EXISTING_CONFIG_PATTERN` — the three settings already exist in `AppConfig`; the proposal only makes their surface typed and coherent.

## 5. Typed graph zoom and pan interaction policy

- **Current NativeHA behavior:** `AppConfig.graphMaxZoomVisibleSamplePercentage = 0.10` participates in sample-count-based maximum zoom. `CardViews.maxGraphZoom` also hardcodes a 30-minute minimum visible time range; `panDelta` hardcodes divisor `900`; zoom/live-edge thresholds use `1.01`, `1.05`, and `0.995`. These independent literals collectively define interaction feel and bounds.
- **Relevant hass behavior/default:** `ha-chart-base.ts` uses ECharts `dataZoom` with `filterMode: "none"`; there is no matching 30-minute reference limit. The provenance-corrected ledger records the user's feature-specific preference for smooth native macOS scrolling/inertia and continuous graph response, but not these exact numeric values.
- **Proposed `AppConfig` surface:** `static let graphInteraction = GraphInteractionPolicy(minimumVisibleSampleFraction: 0.10, minimumVisibleDuration: 30 * 60, panPointsPerFullRange: 900, zoomActivationThreshold: 1.01, liveEdgeThreshold: 0.995)`. Default preserves current behavior.
- **Alternatives and purpose:** shorter minimum durations support close inspection of dense sensors; a fixed maximum zoom provides predictable behavior independent of sample rate; pan sensitivity can be tuned for trackpads versus mice; timeline and numeric graphs can use separate bounds if testing proves that useful.
- **Implementation touch points:** replace the existing `AppConfig` scalar and literals in `maxGraphZoom`, `panDelta`, zoom indicator visibility, `isZoomedAwayFromLiveEdge`, both dashboard/detail graph interaction paths, and interaction tests.
- **Test/validation impact:** parameterize `testPanDeltaGetsFinerAtHigherZoom` and anchored-zoom tests; cover sparse/dense/timeline histories, every boundary, wheel/trackpad deltas, and intermediate animation frames. Confirm default results remain unchanged.
- **Risk:** conflicting sample- and time-based caps can make limits surprising; excessive sensitivity causes jumps; bad thresholds can flap live-edge state or disable zoom. Values need normalization and documented precedence.
- **Provenance:** `EXISTING_CONFIG_PATTERN` — one controlling value is already in `AppConfig`; grouping the verified related literals is suggested, while the user's interaction preference supplies the reason for making the policy explicit.

## 6. Server timeout, failover, and reconnect policy

- **Current NativeHA behavior:** `HomeAssistantConfiguration.init` defaults `timeout` to 10 seconds. `DashboardViewModel.firstWorkingConnection` tries `AppConfig.baseURLs` serially in listed order. `HomeAssistantWebSocketClient` has no reconnect loop; a receive failure leaves status `Disconnected`. None of these operational policies is represented in `AppConfig` beyond the URL list.
- **Relevant hass behavior/default:** `node_modules/home-assistant-js-websocket` 9.6.0 defaults initial `setupRetry` to 0, then automatically reconnects established connections with delays `min(tries, 5) * 1000` milliseconds and resubscribes. `src/data/history.ts` rebuilds a fresh stream and recomputes its start time after reconnect.
- **Proposed `AppConfig` surface:** `static let connectionPolicy = ConnectionPolicy(requestTimeout: 10, endpointFailover: .ordered, initialRetryCount: 0, reconnect: .disabled)`, preserving current NativeHA. Suggested reconnect cases include `.disabled`, `.hassLinear(step: 1, cap: 5, maximumAttempts: nil)`, and a bounded exponential variant with jitter. `NativeHACore` should remain independent of `NativeHAMac`; the app passes configured timeout into `HomeAssistantConfiguration` and an app-level connection supervisor consumes retry policy.
- **Alternatives and purpose:** shorter timeouts improve failover among local endpoints; ordered versus race-first-success affects startup latency/load; hass-like infinite reconnect favors unattended dashboard use; bounded retry is useful in tests or battery-sensitive contexts. Invalid-auth must always be fatal, not retried.
- **Implementation touch points:** `AppConfig`, `DashboardViewModel.firstWorkingConnection/load`, `HomeAssistantConfiguration` construction, the module-02 WebSocket multiplexer/supervisor, resubscription registry, status UI, and cancellation on shutdown/profile change.
- **Test/validation impact:** simulate timeout, refusal, auth failure, disconnect/reconnect, endpoint fallback, cancellation, and resubscription without duplicate events. Use a fake clock for exact delay sequences and a live smoke test for disconnect recovery.
- **Risk:** retrying non-idempotent service calls or duplicating subscriptions is dangerous; racing endpoints increases load; infinite retry can hide persistent configuration errors. The policy must distinguish connection establishment, subscriptions, and commands.
- **Provenance:** `AGENT_SUGGESTED_FOR_SELECTION` — reconnecting is required for reference parity in the rescue plan, but the choice to expose these operational values through `AppConfig` is an agent proposal.

## 7. Prepared graph-series cache budget and eviction policy

- **Current NativeHA behavior:** `GraphPreparedSeriesCache` in `GraphRendering.swift` is a process-wide singleton with hardcoded `limit = 96`. It tracks insertion order and evicts the oldest inserted key, not the least recently used key. The limit is entry-count based even though histories can vary greatly in size.
- **Relevant hass behavior/default:** hass-frontend/ECharts maintains chart-instance data and caches in several layers, but the inspected reference path does not expose an equivalent global 96-entry prepared-series limit. This is a Swift architecture/resource decision.
- **Proposed `AppConfig` surface:** `static let graphPreparedCache = GraphPreparedCachePolicy(maxEntries: 96, maxEstimatedBytes: nil, eviction: .fifo)`, preserving current behavior. Prefer allowing a byte budget and `.lru` once measurement supports reliable size accounting.
- **Alternatives and purpose:** smaller budgets reduce memory on constrained machines; larger budgets improve view/range switching; LRU better retains actively revisited graphs; disabled caching is valuable for correctness diagnostics and cache-effect benchmarks.
- **Implementation touch points:** inject the policy when constructing/accessing `GraphPreparedSeriesCache`, update hit recency if LRU is selected, estimate point/cache storage for a byte budget, expose reset/statistics to tests, and include profile/config changes in invalidation.
- **Test/validation impact:** assert exact FIFO default behavior, LRU order, byte/entry limits, concurrent access safety, incremental-update correctness after eviction, and bounded memory across many entities/ranges. Compare cold versus warm performance.
- **Risk:** too small a cache causes CPU churn; too large retains histories; incorrect size estimates mislead; mutable global policy makes tests order-dependent. Configure it once at startup or make cache instances explicit.
- **Provenance:** `AGENT_SUGGESTED_FOR_SELECTION` — the hardcoded limit is verified, but no user-authored instruction names the cache budget.

## 8. Graph axis range and tick-density policy

- **Current NativeHA behavior:** `GraphBitmapRenderer` hardcodes five x-axis ticks. `niceAxis(values:)` applies 8% span padding with a 0.01 minimum, divides the padded range by four for a rough y step, and rounds to 1/2/5/10. Plot margins are separately fixed at left 42, top 18, right 12, and bottom 26 points. Tests currently assert exact ticks and plot geometry.
- **Relevant hass behavior/default:** `ha-chart-base.ts` delegates tick generation/layout to ECharts, requests overlapping time labels be hidden, and supports Lovelace `min_y_axis`, `max_y_axis`, `fit_y_data`, and logarithmic options. It does not impose NativeHA's fixed count of five.
- **Proposed `AppConfig` surface:** `static let graphAxis = GraphAxisPolicy(xTickTarget: 5, yIntervalTarget: 4, rangePaddingFraction: 0.08, minimumAbsolutePadding: 0.01, density: .fixed)`, preserving current output. Per-card Lovelace min/max/log behavior must still override or compose according to reference semantics rather than being replaced by this global preference.
- **Alternatives and purpose:** `.adaptive(minLabelSpacing:)` avoids overlap at narrow widths; compact/dense presets support different dashboard sizes; zero padding is useful for exact bounded sensors; a configured minimum-zero policy can serve selected measurement views. The setting controls presentation density, not the underlying values.
- **Implementation touch points:** `GraphBitmapRenderer.render`, `niceAxis`, `linearTicks`, axis overlay label measurement, plot-margin calculation if adaptive labels need it, Lovelace graph options from module 04, render/cache tokens, and graph tests.
- **Test/validation impact:** cover narrow/wide sizes, negative/constant/large/small values, long units, fixed Lovelace bounds, no-overlap behavior, and default snapshot/tick equivalence. Include locale-dependent label widths when formatting is implemented.
- **Risk:** global bounds can hide data or violate Lovelace semantics; excessive ticks clutter; adaptive measurement can destabilize layout between frames. Invalid padding/tick counts must be rejected or clamped.
- **Provenance:** `AGENT_SUGGESTED_FOR_SELECTION` — the literals and reference differences are verified, but this configuration surface was not directly requested by the user.

## 9. Typed fixed-or-responsive dashboard layout policy

- **Current NativeHA behavior:** `AppConfig` separately defines sidebar width 238, column count 3, column width 496, gap 12, and outer padding 16. `DashboardView` always builds those fixed-width columns inside a two-axis `ScrollView`; `DashboardViewModel.dashboardColumns` places unassigned cards in the shortest column. `NativeHAMacApp` separately hardcodes a 1200-by-760 minimum window.
- **Relevant hass behavior/default:** `src/common/util/responsive-columns.ts` uses a 320-pixel minimum column width and 16-pixel default gap to derive column count. Lovelace views also carry their own layout/panel semantics, so this is only a native fallback policy, not a replacement for decoded view configuration.
- **Proposed `AppConfig` surface:** `static let dashboardLayout: DashboardLayoutPolicy = .fixed(sidebarWidth: 238, columnCount: 3, columnWidth: 496, gap: 12, outerPadding: 16, minimumWindow: CGSize(width: 1200, height: 760))`, exactly preserving current behavior. Add `.responsive(minColumnWidth:maxColumns:gap:outerPadding:sidebarBehavior:)` as an alternative.
- **Alternatives and purpose:** fixed mode maintains today's carefully arranged desktop composition; responsive mode serves smaller windows and other Macs; collapsible/hidden sidebar behavior gives content more space; max columns prevents ultra-wide fragmentation. Keeping this one typed policy prevents incompatible independent constants.
- **Implementation touch points:** consolidate `AppConfig` constants, `NativeHAMacApp`, `DashboardView` geometry/layout, column assignment recomputation, sidebar presentation, and module-12 Lovelace view handling.
- **Test/validation impact:** render fixed default and responsive boundary widths, verify stable card order during resize, no clipping, correct scroll behavior, panel/single-column views, and layout changes after profile/view switches. Keep existing 496-point card fixtures.
- **Risk:** resize-driven reflow can move controls under the pointer and invalidate graph sizes/renders; shortest-column packing can reorder visually; overly broad global layout rules can conflict with Lovelace view configuration.
- **Provenance:** `EXISTING_CONFIG_PATTERN` — five fixed layout values already live in `AppConfig`; the typed fixed/responsive choice is the proposed extension.

## 10. Graph updates while viewing historical (off-live-edge) data

- **Current NativeHA behavior:** `BitmapLineChart.scheduleRenders` discards a live data-triggered rerender when `isZoomedAwayFromLiveEdge` is true (`zoomScale > 1.01 && panFraction < 0.995`). Data continues changing upstream, but the visible bitmap stays frozen until another viewport/render trigger. There is no pending-update indicator or explicit policy.
- **Relevant hass behavior/default:** `state-history-chart-line.ts` and `ha-chart-base.ts` gate and merge updates around chart windows, but the inspected reference does not define an equivalent user-selectable "freeze when panned" policy. This is a NativeHA interaction/performance decision.
- **Proposed `AppConfig` surface:** `static let historicalViewportUpdates: HistoricalViewportUpdatePolicy = .deferUntilViewportChange`, preserving current behavior. Suggested cases: `.deferUntilViewportChange`, `.renderInPlace(coalescing:)`, and `.deferWithPendingIndicator`.
- **Alternatives and purpose:** freezing protects interaction and keeps the historical view stable; rendering in place suits live monitoring even while zoomed; a pending badge makes staleness explicit and lets the user apply updates. This is behaviorally meaningful because it determines whether visible data is current.
- **Implementation touch points:** `BitmapLineChart.scheduleRenders`, data/render token bookkeeping, a pending-update state and optional overlay, return-to-live-edge behavior, cancellation/coalescing, and both dashboard/detail graphs.
- **Test/validation impact:** feed live points while panned and assert each policy's bitmap/token/pending state; verify no lost final update on return, no render storm, stable hovered timestamp, and continuous interaction priority. Use animation-frame or event-to-render checks for the visible transition.
- **Risk:** silent freezing misleads users; in-place updates can shift axes and cause jank; a pending queue can grow or apply stale generations. The implementation should retain only the newest generation, not every event.
- **Provenance:** `AGENT_SUGGESTED_FOR_SELECTION` — this is a verified implicit production policy with a credible user-facing purpose, but it was not directly named by the user.

## Selection note

Candidates 1 and 2 should be promoted first because they are direct user instructions. Candidate 3 is the safest next performance knob only if its default remains full backing resolution. Candidates 4, 5, and 9 mainly organize values already treated as configuration. Candidates 6, 7, 8, and 10 should be selected only if their alternative modes are expected to be used; otherwise moving the current literal into `AppConfig` would add surface area without product value.
