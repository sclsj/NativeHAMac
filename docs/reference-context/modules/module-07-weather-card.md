# Module 07 evidence packet

## Gate and bounded scope

Contract revision 1 completed and independently verified the existing `weather-forecast` card's **current conditions** under C07-01 through C07-08 and C07-11. Those contracts remain green and unchanged. At the revision-2 research base, activating that card exposed the user's next observed gap: `EntityDetailSheet` had no weather route and fell through to generic state plus raw attributes, whereas hass-frontend routes weather to `more-info-weather`.

Contract revision 2 records the completed additional milestone: a native weather more-info surface for the selected detail entity, including the single modal-scoped forecast subscription needed for parity. It covers the current condition header, relative-time presentation, formatted pressure, humidity, wind, and visibility rows, supported forecast-type selection and tabs, forecast presentation, attribution, error/sentinel behavior, accessibility, and exact open/switch/close/reconnect cancellation ownership.

This revision does **not** activate the Lovelace card forecast contracts C07-09/10. All three dashboard cards continue to honor raw `show_forecast:false`; they start zero forecast owners and render no forecast row. Detail forecast identity is selected entity + forecast type + opaque detail generation, never card identity. No cache, persistence key, setting, profile, service call, or typed `AppConfig` surface is added. Core Graphics stays the primary graph renderer and every approved graph-range, history, graph-feed, render-coordinator, tooltip, logging, Module 04/12 identity, and fixed-bootstrap policy remains unchanged.

Out of scope: dashboard-card forecast rows/owners, radar/maps, animated weather, exact MDI/SVG asset reproduction, arbitrary Lovelace actions, editing entity or weather configuration, any state-changing service call, Modules 08-11, and the separate Module 09 stale-viewport fallback.

## Reference decisions and corrections

- Runtime `show_current` and `show_forecast` both default true. The editor's normalization is not runtime authority. Without forecast data, current conditions render even when `show_current: false`.
- The current card renders one configured/fallback secondary attribute. The pressure/wind/visibility/attribution list in `more-info-weather.ts` belongs to the detail dialog and is not card scope.
- A modern card `forecast_type` causes hass-frontend to subscribe even if card forecast is hidden. NativeHA continues to defer **dashboard-card** forecast ownership and issues no forecast command merely for a mounted card. Revision 2 adds a separate selected-detail owner because hass-frontend's weather more-info subscribes independently of Lovelace `show_forecast`.
- hass-frontend leaves both `unknown` and `unavailable` weather cards actionable. NativeHA follows that reference behavior: missing entities remain non-actionable, while neither sentinel suppresses an otherwise enabled action.
- hass-frontend routes `weather` through `state_more_info_control.ts` to `more-info-weather`; NativeHA's absent weather switch case is the direct cause of the generic raw-attribute sheet the user observed.
- Weather more-info chooses one forecast type, not one owner per supported type. `getDefaultForecastType` prefers daily, then twice-daily, then hourly; changing tabs replaces the old subscription. The live entity advertises bits `3`, so its reference detail defaults to Daily and also offers Hourly.
- The specialized reference control suppresses generic history/logbook content. Revision 2 likewise adds no weather detail-history subscription or graph. Dashboard graph rendering and the separate Module 09 fallback are untouched.

## State machines

### Completed current-card milestone

`resolved card -> pure config adapter -> entity lookup -> missing/sentinel or current presenter -> SwiftUI render`. Accepted global entity state continues to come from Module 05. The mounted dashboard card still adds no async state, owner, startup, cancellation, cache, persistence, or generation.

### Revision-2 detail state

`closed -> selected current content -> forecast starting -> forecast subscribed -> reconnecting/error -> closing -> closed`. Unsupported forecast features stop at selected current content with no owner. Loading/error affects only the forecast region; accepted current entity content remains available.

The desired request is exactly one `(entity ID, forecast type)` selected by the open detail. An opaque generation distinguishes close/reopen and A -> B -> A. On type/entity replacement: revoke the old generation and desired key, clear old forecast publication, detach and cancel startup/subscription, await cleanup on `dashboardOwnerOperationTail`, recheck the final desired request plus app/config/lifetime authority, then start/install only that request. Closing, active-view/config replacement, stop, and deinit execute the same invalidation and cancellation boundary. Module 02 alone handles physical reconnect and wire ID replacement for an installed logical subscription.

### Deferred dashboard-card forecast lifecycle

`inactive -> desired -> starting -> subscribed -> reconnecting/cancelling -> inactive`. The only authority is an opaque owner generation plus exact request membership on the existing owner tail. Module 02 owns physical-generation resubscription and fresh wire IDs. Cancellation is idempotent and settles before replacement. Event datetimes label forecast items only.
